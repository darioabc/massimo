# massimo: adopt

A repo that already keeps its own design-system data should not lose it, or have it copied into a second system that drifts. Adopt keeps what works, drives it through massimo's config, and proves massimo reads the repo exactly as the repo's own tools do before anything is switched over. Nothing old is removed until a dry run finds nothing that still depends on it, and the user says yes.

Plugin root: two directories above this skill's base directory. Follow `<plugin>/reference/project.md` → Session protocol. `<project>` is the project folder: `projectDir` in `massimo.config.json`, `design-system` by default. Every command below is `node <project>/scripts/adopt.mjs <command>` unless it names another script.

## Where adopt stands

The ledger, `<project>/adopt/ledger.json`, is the source of truth. Each class (graph, stories, audit, tokens, docs) moves through found, mapped, shadowed, proven, cut-over and retired, one state at a time, with `mark`. The adopt phase in `state.json` follows the ledger by itself: never set it by hand, except to skip it. At the start of every session run `status` and tell the user, in two or three lines, which class is where and what is next.

## The flow

| Step | Commands | The user approves |
|---|---|---|
| 1. Scan | `scan` | what was found, and who depends on it |
| 2. Plan | `plan`, `status`, `mark <class> mapped` | each loss that is not clean, class by class |
| 3. Configure | `config`, `config --write` | the config diff |
| 4. Shadow | install the shadow workflow, `mark <class> shadowed` | the workflow file |
| 5. Prove | `verify <class>`, `accept`, `mark <class> proven` | each verify table, and each accepted difference |
| 6. Cut over | one batch per class, `mark <class> cut-over --batch <id>` | each batch's diff, before its commit |
| 7. Retire | `retire <class> --dry-run`, `historical <path>`, `mark <class> retired` | each retirement, as its own decision |

1. **Scan.** `scan` reads the repo without running any of it and writes `<project>/adopt/inventory.json` and `inventory.md`. Before init it prints the inventory instead (`node <plugin>/scripts/adopt.mjs scan`). Summarise it: the story lane or story tools, the `ds:` header keys beyond the built-in ones, the repo's own generated files and the script that writes them, and the consumers by class (deploy, ci, hand-run, docs). Ask the user whether anything is missing: a path built at run time escapes the text search, and the deploy build and CI of each cut-over batch are the backstop for it.
2. **Plan.** `plan` writes the ledger and `<project>/adopt/config.proposed.json`, and prints the ledger. Go class by class. For each asset, say its decision (keep, convert or retire) and its loss (clean, carried, lost or blocker) with the lines that explain it. The user agrees each loss that is not clean, or changes the decision or the loss in the ledger by hand. A blocker stops its class at mapped until it is resolved. For the audit class, show `audit.verify` in the ledger: the repo's ratchet, the map of its rules to massimo's kinds that plan proposed from the rule names, and the rules with no kind, which stay the repo's (as a project check under `guard.extraChecks`, or a loss the user accepts). Edit the map by hand where a rule needs more than one kind, such as `raw-colour=color+tailwind-palette`. Record each agreement with `state.mjs decide`, then `mark <class> mapped`.
3. **Configure.** `config` prints the proposal as a diff against `massimo.config.json`; on the user's OK, `config --write` adds it, never overwriting a value they set. Then fill in what scan cannot know, with the user: `graph.taxonomy.rules` for the files with no `ds:group` line, the taxonomy's placement text and `notLive`, `stories.componentless`, the audit settings (`audit.kinds`, `audit.exempt` by role, tier or group), and `tokens.mirror`, `tokens.inventory` and `tokens.breakpoints` where the repo's style files stay the source. When the config turns on a key from 0.3.0 (`tokens.mirror`, `tokens.inventory`, `audit.kinds`, `graph.strictFaults` and the like), set `"minScripts": "0.3.0"` at its top, so older vendored scripts refuse the config instead of misreading it. Then build massimo's outputs, in this order: `tokens.mjs mirror`, `tokens.mjs build` and `tokens.mjs resolved` where they are on (`tokens.mjs check`, which `ds:check` runs, wants the build's outputs too), then `graph.mjs` (it records the token set, so a mirror written after it leaves it stale), then `audit.mjs --import <ratchet> --map <map>` to compare the audit (it writes nothing without `--write`, and its story kinds count what `graph.json` holds).
4. **Shadow.** For GitHub Actions, copy `<plugin>/templates/design-system-shadow.yml` to `.github/workflows/design-system-shadow.yml`, replace `<project>` with the project folder, and match the Node version and install step of the repo's other workflows. It runs on pull requests only and never blocks: `ds:check` and `adopt.mjs verify` beside the repo's own checks, both allowed to fail. It grows by itself as classes land, since `check.mjs` runs each check once its files exist. For another CI system, add an equivalent job that is not required and show the user. Tell the user it runs on their next pull request; never push. Once a pull request has run it for a class, `mark <class> shadowed`.
5. **Prove.** `verify <class>` (or `verify` for all four) prints a table of what it compared and every difference, and exits 1 on any difference the ledger has not accepted. Show the user each table. For each open difference, fix its cause (the config, or the code), or, on the user's word, accept it with their reason: `accept <class> '<key>' --why '<reason>'`, the key exactly as verify printed it. A class whose cut-over changes the story lane or its chrome also gets a visual proof: `verify stories --pairs <file> --a <base url> --b <base url>` writes a pairs file from the manifest (each entry at light and dark, at 390 and 1440 wide, on its frame route when it has one, and the tier `--dom-tier` names, Pages by default, compared by page text), and `--shoot` runs it through `shoot.mjs`, with `--playwright <path>` when the repo has no Playwright of its own. Serve the lane from the main branch for `--a` and from the adopt branch for `--b`. Verify records nothing: when it passes and the shadow job has run for as long as the user chose to soak it, `mark <class> proven`. For the audit, a proven class records its baseline from the ratchet: `audit.mjs --import <ratchet> --map <map> --write`.
6. **Cut over.** One class per batch, consumers before producers: first what reads the old outputs at build or run time (the deploy consumers the ledger names), then the CI jobs, then the docs, and the producer last. A generated doc that names an asset changes through its writer, then is regenerated, as the ledger's line says. Each batch is one commit whose message ends with a trailer, `Adopt-Batch: <id>`, the id being the class and a number, such as `graph-1`. Run the repo's own build and checks, show the user the diff, and commit on their OK. Then `mark <class> cut-over --batch <id>`: the ledger keeps the id, so `git log --grep 'Adopt-Batch: <id>'` finds the commit and one `git revert` undoes it.
7. **Retire.** Only after cut-over, and only on the user's OK for this class. `retire <class> --dry-run` lists what goes (the assets marked retire, and those marked convert, whose place massimo's output takes), the package scripts that run them, the workflow jobs that run those scripts, files a retiring generator also writes for another class, and every consumer still outside the docs the ledger marks historical. It exits 1 while any remains: repoint each, or, on the user's word, mark a doc that only records how things were with `historical <path>`. Once the dry run is clean, remove what it lists in one commit whose trailer reuses the class's batch id with `-retire` (`Adopt-Batch: graph-1-retire`), so the same search finds both commits. Then `mark <class> retired`. `retire` without `--dry-run` refuses: deleting is this step's job, never the script's.

## Rules

- Consumers before producers, always. A producer is removed only when its dry run is clean.
- One class per batch, one commit per batch, each with its `Adopt-Batch` trailer. Never mix a cut-over with a retirement.
- The repo's own story lane stays where it already meets massimo's lane contract (the stories skill): native, gated, discoverable, states side by side, real content. Configure massimo to read it through `stories.lane`, `stories.manifest`, `stories.pages` and `stories.frames`; never scaffold over it.
- Never push, open a pull request or merge. Branch protection, such as making `ds:check` a required check, is a setting the user changes (the guard skill says how).
- Retire only on the user's OK, per class, after a clean dry run. A loss the user has not agreed is never retired.
- Accept a difference only with the user's reason, in their words. Never accept one to make a table pass.
- A config that turns on a 0.3.0 key sets `"minScripts": "0.3.0"`.

## End of a session

Follow the session protocol's End steps in `<plugin>/reference/project.md`. The adopt phase's note is rebuilt from the ledger on each `plan` and `mark`, so it needs no `state.mjs set`. Rewrite STATUS.md's hand-written sections: where each class stands, the one next step (the next `verify`, batch or dry run, and `/massimo:adopt` to run it), and any difference or loss still waiting on the user under Open questions. Offer to commit `<project>/adopt/` and the config with a conventional message; a cut-over or retirement batch is committed only as step 6 or 7 says.
