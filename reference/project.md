# The in-repo project

Massimo keeps its working state inside the repo it is improving, so a designer or developer can stop at any point and pick up in a new session, on another machine, or hand over to a teammate, without losing context. Every skill and agent reads this contract.

## Files

`<project>` in every skill and agent is the project folder: `projectDir` in `massimo.config.json`, `design-system` unless the repo already uses a folder of that name for something else (then `.massimo`). Read each path written as `<project>/…` from there.

```text
massimo.config.json            where things are: framework, component globs, style files, story lane, token outputs
<project>/                     the project folder (config.projectDir)
├── STATUS.md                  the hand-off between sessions: where we are, next step, open questions
├── state.json                 machine-readable phase and exploration state (edit only through state.mjs)
├── product.md                 product grounding: users, reference products, brand feel, a11y bar, scope, real-content sources
├── decisions.md               append-only decision log
├── README.md                  how the team uses the system (docs.mjs writes its generated part)
├── graph.md / graph.json      generated component graph (graph.mjs)
├── audits/                    latest.md, latest.json, baseline.json (audit.mjs)
├── tokens/                    the token set in W3C Design Tokens 2025.10: tokens.resolver.json (the entry point), base.tokens.json,
│                              theme/<context>.tokens.json; draft/ from extract; preview.html, figma-variables.json;
│                              resolved.json, the inventory of every custom property per selector (tokens.mjs resolved)
├── kit/kit.css                generated token stylesheet that mockups link to
├── explorations/<topic>/      one folder per design topic in the ux loop (brief.md, round-N/, index.html)
├── handoffs/<topic>.md        translate specs ready to build
├── tidy/backlog.md            the tidy batches, their status and results
├── figma/                     export.json (what the file holds, read by read-library.js), mirror.json (what was mirrored, with ids), drift.md
├── sections/                  further sections of the brand book: the generated ones for tokens the lists cannot hold (motion.md, borders.md,
│                              gradients.md, more-tokens.md, by artifact.mjs pages) and any the team writes
├── components/<Name>/         README.md, a page per component from its graph node (artifact.mjs pages)
├── assets/<Group>/            logos, icons and illustrations, each group with a README.md (the team's)
├── fonts/                     font files to list beyond the ones the story build declares (the team's)
├── artifact/                  kept/ (files copied over every build: an index, a cover), mirror.json (where the folder was published and from
│                              which tokens and graph); project/, files.json and report.md are the build, gitignored
├── playbooks/                 the plugin's skills, agents, references and templates, copied with the scripts so an agent with no plugin
│                              follows the same steps; AGENTS.md at the repo root points at them
├── adopt/                     inventory.json and inventory.md (adopt.mjs scan); ledger.json (adopt.mjs plan): what becomes of each
│                              part of the repo's own setup, where each class stands, the differences accepted with their
│                              reasons and details, the audit's map onto the repo's ratchet, and the docs marked historical;
│                              config.proposed.json (adopt.mjs plan)
├── shots/                     screenshots (gitignored; regenerate any time), except shots/kept/
│   └── kept/<topic>/          screenshots a handoff, brief or baseline links to (committed)
└── scripts/                   vendored massimo scripts, so CI and teammates without the plugin can run them
```

Paths in `massimo.config.json` are relative to the folder that holds it: the repo root, or the package a monorepo's project lives in. `<project>/` is committed. `shots/` is gitignored by `<project>/.gitignore`, apart from `shots/kept/`: a screenshot that a committed file links to is copied there, so a teammate who opens the handoff sees it.

Config keys beyond the paths: `tokens.darkSelector`, `tokens.darkMedia`, `tokens.defaultMode` and `tokens.selectors` (how the app switches theme), `graph.extraKeys` (a repo's own `ds:` header keys), `graph.classLibraries` (extra class-based component libraries, see the graph skill), and `ticketPattern`: a regular expression for the repo's ticket ids (`"PROJ-\\d+"`). When it is set, the graph lists the ticket ids each component file mentions, so a reader can find the why behind a component. `detect.mjs` suggests the dark selector from the class Nuxt's color-mode module sets, else from a Tailwind 3 config's `darkMode` (`class` or `selector`), with `tokens.darkMedia` off, and reports where it read it as `darkMode`.

In a git checkout, every file list the scripts read from leaves out what git ignores, as `git ls-files` does, so build output and a copy of the web build inside a native project are never read as source. The audit still reads those files for the custom properties they define, and for nothing else, so a variable set in a token stylesheet that a build generates and git ignores is not undefined. `detect.mjs` also suggests an `audit.exclude` for folders that hold no UI styling, and suggests no token source from them: a Nuxt app's `server/` folder, and Capacitor's `android/`, `ios/` and its `webDir`. The audit never reads a Tailwind config (`tokens.tailwindConfig`, or any `tailwind.config` file) for raw values: it is a token source, where every value belongs.

In a Nuxt app (`framework` is `nuxt`, or a `nuxt.config` sits at the root), the graph also reads what Nuxt resolves for itself, from the app's and its layers' `nuxt.config` (literal values only): the aliases (`~`, `@`, `~~`, `@@`, `#shared`, `#layers/<name>` and the `alias` option) for an import that neither `aliases` nor a tsconfig path matches, and the components Nuxt auto-imports from each layer's components folders, the `components` option and shadcn-nuxt's `shadcn.componentDir`. A template tag, a `resolveComponent()` call or an import from `#components` that names one is an edge, like an import. `graph.edges: ["!nuxt"]` turns those edges off; the aliases stay. A remote or package layer is a warning. In every project, an import that starts with `@/` or `~/` and resolves to nothing is unresolved, never a package.

Keys for the artifact phase: `artifact.title` (the name on the folder; the repo folder's name when null), `artifact.components` (the tiers or groups whose nodes get a page, as `["Primitives", "Foundations / Brand"]`; null takes every node with a story), `artifact.built` (a static build of the story lane for the previews; null falls back to `stories.outDir`), `artifact.previewSelect` (one element of a story page to keep as the preview, `#id`, `.class` or `[attr]`), `artifact.previewHeight` (px, 320) and `artifact.assets` (`[{ group, include }]`, repo files copied under `assets/<Group>/`).

Keys for a repo that already has its own design-system setup, all inert until set:

- `graph.keys` gives a repo's own `ds:` keys a role: `list`, `definitions` (custom properties a parent or a script sets), `scope` (one value, which audit exemptions can name) or `breakpoint` (`<width> <reason>`). A role is a name, or `{ role, values, under }` to limit a scope to a set or a list to files in a folder.
- `graph.taxonomy` holds the tiers in order, each group with a line on what belongs in it, the placement test, path rules that give a file its group, the parked marker and its group, the keys each tier needs, and `notLive`: the tiers that are not live code (internal modules, parked work), which need no story.
- `graph.kinds` adds node kinds beyond components, such as layouts and pages, each a list of globs. `graph.edges` reads imports beyond import statements: `mdx` (the import lines of MDX files in the consumers) and `glob` (`import.meta.glob` calls). In a Nuxt app, `!nuxt` turns off the edges to the components Nuxt auto-imports, and `nuxt` states the default. `graph.header` is `anywhere` or `top` (only the first comment block counts), and `graph.strictFaults` makes header faults fail the write and `--check`.
- `stories.manifest`, `stories.pages` and `stories.frames` point at a lane's own list of stories and where each slug's page and frame live; `stories.lane` is then `manifest`. `stories.componentless` lists the places (`Root / Group`) where a story may name no component, such as token pages. A story's root is one of `graph.taxonomy.tiers` (any root when there are none); there is no separate list of story roots.
- `audit.kinds` turns kinds off (`false`), or the Tailwind palette kind on (`true`, with the Tailwind config's colours as the repo's own; a token then makes a class such as `text-red-600` the repo's own only when a Tailwind output builds it or the config names it). Turned on, the palette kind also runs in an app whose colours come from a class library such as daisyUI, and when it still finds no colours to hold the palette against, `latest.md` says it was turned on. With the kind on, every palette class outside the repo's own colours is a finding, and so it is by default in a Tailwind 4 app whose style files declare `--color-*` colours of their own. Otherwise a palette class is a finding only when a colour token holds the colour it renders in the default theme, with that token as its fix (`token` on the finding, a semantic token ahead of the primitive it aliases), and the others are counted under `paletteClasses` in `latest.json` and in `latest.md`, never in the baseline; before the repo has colours of its own, every palette class is counted there. A Tailwind config that sets `theme.colors` of its own (not from `tailwindcss/colors`), or a `@theme` that resets `--color-*`, replaces Tailwind's palette, and the kind is skipped. `audit.exempt` skips a kind in a file by a scope role's value, its tier or group, or a glob. `audit.arbitrary` limits arbitrary values to colours, a role read such as `text-[color:var(--x)]` included. `audit.primitives` limits primitive reads to colours, and `'color'` picks colour primitives by their collection, whether or not a token aliases them; with no token set yet, a primitive is then a literal colour the style files define, read outside them. `tokens.mjs extract` proposes from the audit without these four settings. `audit.failWhenBehind` fails `--check` while the baseline is behind the code. With `stories.manifest` set, the audit also counts the story lane's policy problems that the graph writes to `graph.json` (`story-title`, `story-files`, `story-states`, `no-story`); a manifest the graph could not read leaves all four unmeasured, and a check the graph could not make (`storyLane.notChecked`) leaves its kind unmeasured, so `--lower` never records their drop. A baseline that tracks a kind added in 0.3.0, such as `breakpoint` or the story kinds, is format 2, which older scripts refuse.
- `guard.extraChecks` lists project commands `ds:check` runs as well, and `tokens.breakpoints` (`{ scale, twins }`, widths in rem, px or em) is the width scale the breakpoint audit holds the code to: an `@media` width, or a Tailwind screen or `min-[...]:` or `max-[...]:` variant, off the scale and its twins is a finding unless the file's header allows that width through the breakpoint role. Screen names come from `tokens.tailwindConfig` when it sets screens, else Tailwind's defaults; Tailwind 4 screens (`--breakpoint-*` in `@theme`) are not read yet.
- `tokens.mirror` keeps the style files as the source: `tokens.mjs mirror` writes the token set at `tokens.source` from them, and every other command reads that set. Each token keeps its CSS name, its themes follow the config's theme selectors, a value under any other selector (a band, a tone, a phone-width override) goes in its `$extensions.massimo.scopes`, and the comment on its root declaration (just before it, or after it on its line) is its description, unless it opens a section. Where two selectors the config places in one theme set different values (the dark class and the dark colour-scheme query), the theme takes the first and the other keeps its value as a scope, with a note. A `light-dark()` on the root stays one declaration. `tokens.mjs check` then fails while the mirror is behind the CSS, and `build` refuses an output that would write over a file it mirrors, or one the style files' globs would read once written.
- `tokens.inventory` sets what `tokens.mjs resolved` lists in `tokens/resolved.json`: every custom property the sheets declare, with its file, layer, family and a value per selector (each member of a selector list on its own), each colour resolved in its theme through its own sheet and the sheets `tokens.styleFiles` names, never another listed sheet, plus the type classes, the `@font-face` rules and `tokens.breakpoints`. `files` are the sheets (globs). `layers` names each layer in order with its file globs, or `{ files, names, selectors }` to place by property name or by the selector a property is first declared under. `families` names families by property-name globs, ahead of massimo's own. `typeClasses` are class-name globs; without them, a type class is any class that is a selector on its own in a rule setting a size, line height, weight or family. Without the key, the inventory lists `tokens.styleFiles` as one layer. `tokens.mjs check` keeps the file current when this key or `tokens.mirror` is set. Scripts older than 0.3.0 ignore both keys, so a config that sets either also sets `minScripts` to `0.3.0`.

The story lane's basic keys, for every lane kind: `stories.lane` is `native` (the default: stories are found by file name), `manifest` or `csf`; any other value warns in the graph and is refused by `stories.mjs`. `stories.include` is the globs of story files (default `src/**/*.story.{tsx,jsx,ts,js,vue,svelte,astro}`; on a csf lane, the CSF files, such as `src/**/*.stories.{tsx,ts}`). `stories.devCommand` (default null) is the command that serves the lane, which the visual proof starts. `stories.port` (default `4650`) is its port. `stories.url` (default null) is where the lane opens. `stories.storyUrl` (default null) is a story's address with `{slug}`, and with `{state}` on a csf lane, which serves one state per document; when it is null the route comes from `stories.url`. Beside a Storybook the repo keeps, it is Storybook's story address with `{id}`, the story's Storybook id (`<url>/iframe.html?id={id}&viewMode=story`), which `stories.mjs storybook` fills in.

Keys for the csf story lane, all inert until set. A config that sets any of them to a non-default value, or sets `stories.lane` to `csf`, also sets `"minScripts": "0.4.0"`, and `adopt.mjs config --write` raises it by itself. Scripts older than 0.4.0 refuse that config instead of ignoring the keys. The csf lane reads story files in place and never copies them; `skills/stories/recipes/vite-csf.md` says how it is built.

- `stories.ids` (default `export`): the id of a state is `<slug>--<state>` from the file's title and the export's name. `ladle` follows Ladle's rule, the storyName first, so ids that links and specs already use stay the same.
- `stories.order` (default null): id-prefix globs that set the order of the index, as Ladle's `storyOrder` does. Then the title, the file path and the order of exports.
- `stories.home` (default null): the id that `/` and `/stories` open.
- `stories.viewports` (default null): `[{ label, width, height }]` in px, where a width of `0` fills the pane. Null gives Phone 390x844, Desktop 1440x900 and Full. The shell shows each state in an iframe of one of these sizes.
- `stories.sideBySide` (default `[]`): globs of story files whose states the shell may show together. Every other file shows one state at a time.
- `stories.switchers` (default `[]`): `[{ name, label, attribute, values, unset, default }]`. Each switch sets `attribute` on `<html>`; the `unset` value removes it; a `default` of null asks the frame's `switchDefaults`. A switch with `attribute: null` sets nothing, and the frame applies its value from its `switches` prop, as a class-based theme needs (the vite-csf recipe shows how). Never `attribute: "class"`, which would replace every class on `<html>`.
- `stories.banners` (default null): `{ <meta key>: { tone, lead } }`. A state whose merged meta sets that key to a non-empty string shows the banner.
- `stories.frame` (default null): a project module whose default export wraps every state.
- `stories.storyOnly` (default `[]`): globs of modules only stories use, beyond the ones the import graph finds. `stories.mjs --check` fails when app code imports one, once `stories.appCss.base` is set.
- `stories.appCss` (default null): `{ base, entry }`, the CSS the lane imports and the app's own entry that holds its `@source not` lines (`entry` may be null). The lane never imports a file that holds `@source not`. `stories.mjs --check` reads the CSS layout and the story-only imports only when `base` is set.
- `stories.outDir` (default null): the lane build's output folder, `dist-stories` in the recipe. `stories.mjs leak` refuses a folder git does not ignore.
- `stories.hostFiles` (default `[]`): `["_redirects"]` makes the build write one rewrite, for `/stories/*` only. No other name is supported.
- `stories.frozen` (default `[]`): `[{ file, sha256, since }]`, design targets kept byte for byte. `stories.mjs --check` fails while a file's hash differs. `adopt.mjs convert stories` lists the candidates, `convert stories --freeze <file>` pins one, and `--refreeze <file>` pins it again.
- `stories.policy` (default null): the checks below. Each option is off until it is set, and an option massimo does not know, or a pattern that does not compile, is a warning in the graph.

`stories.policy` options, all absent by default. The graph reads them on a csf lane and reports a break as a `story-title`, `story-own`, `story-banner` or `story-files` problem in `graph.json`.

- `roots`: the allowed first parts of a title. The check is off until this is set; it does not follow `graph.taxonomy.tiers`.
- `titleParts`: `{ default: 3, <Root>: n }`, the number of parts a title has, by root. A root with neither its own number nor a `default` is not checked. `titleExact`: titles allowed outside that count.
- `titleText`: `{ pattern, forbidden: [{ pattern, flags, what }] }`. `pattern` must match every title part and every state name (the storyName, else the export); no `forbidden` pattern may match either, and an export with no storyName is also tested in words. `what` is the phrase a problem uses.
- `nameMatches` (`true` or off): a story file beside a graph node is titled `<node group> / <node name in words>`, with names compared by letters and digits only, in any case. A title rooted in a root named in `bannerByRoot` is exempt, since such a story is not about the node beside it, and so is a node in a `graph.taxonomy.notLive` tier. Without `bannerByRoot`, no root is exempt. `names`: `{ <file stem>: <name> }` gives a node the name its story takes.
- `ownStory`: `[{ tiers, files, link }]`. A live node in one of the tiers, or matching one of the file globs, needs a story of its own. `link: "own"` (the default) accepts a story file beside it or one titled `<node group> / <name>`; `sibling` accepts the file beside it only. A node with a `ds:no-story` line is skipped.
- `bannerByRoot`: `{ <Root>: <meta key> }`. A file titled under that root sets the key to a non-empty string on its default export, and no state outside it has the key in its merged meta.
- `titlePrefix`: `[{ files, prefixes }]`. The titles of those story files start with one of the prefixes.
- `cleanIds` (`true` or off): every id splits on `--` into one folder per title part plus the state, with none empty and none starting or ending in a hyphen.

A `no-story` node, a live node with no direct story and no `ds:no-story` line, is always reported in a csf lane. It is reported and never fails a run, even with `graph.strictFaults`. `stories.mjs --check` runs after the graph in `ds:check` and also fails on a registry fault, such as a duplicate id; graph.json records the same problem, so the graph line fails too until `graph.mjs` is run again, and it keeps failing after that only with `graph.strictFaults`.

## Phases

`state.json` tracks nine phases in this order. Each has one skill.

| id | skill | done when |
|---|---|---|
| `setup` | `start` | config, product.md and the project folder exist |
| `adopt` | `adopt` | optional, to do only when the repo has a setup of its own; every class in `adopt/ledger.json` (graph, stories, audit, tokens, docs) is cut over or retired, each having moved through found, mapped, shadowed and proven. The ledger is where adopt stands; the phase note is a view of it, rebuilt on each `adopt.mjs plan` and `mark` |
| `graph` | `graph` | graph.md is generated and its unresolved-import list is empty or explained |
| `stories` | `stories` | the native story lane runs and the agreed set of components has baseline stories |
| `tokens` | `tokens` | tokens.json exists, builds into the repo's styling, and the user approved each group |
| `tidy` | `tidy` | the tidy backlog is cleared, or the user parked what is left |
| `guard` | `guard` | `ds:` rules on the primitives, `ds:check` in CI, <project>/README.md written |
| `figma` | `figma` | optional; tokens and primitives mirrored, mirror.json recorded |
| `artifact` | `artifact` | optional, skipped until the user wants it; the pages are written, the folder is built and published, `artifact/mirror.json` recorded |

Status values: `todo`, `in_progress`, `done`, `skipped`. A user can skip any phase at setup or later. A project without an `adopt` entry (made before 0.3.0) has it as skipped, and STATUS.md and the session hook leave out an optional phase skipped that way. The `ux` loop is not a phase: it runs whenever there is a surface to design, and its topics live in `state.json` → `explorations`.

## Scripts

Before setup, run scripts from the plugin: `node <plugin-root>/scripts/<name>.mjs`. After setup, run the vendored copy: `node <project>/scripts/<name>.mjs`. They are the same files; `init.mjs --update-scripts` refreshes the vendored copy when the plugin is newer.

A script finds the project from the folder it runs in: the nearest folder from there up to the repo root (git toplevel) that holds `massimo.config.json`, else the git toplevel. `--root <dir>` names the folder instead. So a project made with `init.mjs --root <package>` in a monorepo works from inside that package: its npm scripts, the session hook when Claude starts there, and the commands the scripts print. Its config paths are relative to that package. A script run from the repo top does not see a project kept in a package: run it from inside the package, or pass `--root <package>`.

The plugin root is two directories above a skill's base directory (`<plugin-root>/skills/<skill>/`). Agents receive it in their dispatch prompt.

| script | does |
|---|---|
| `detect.mjs` | reads the repo and prints the stack as JSON, with a suggested config, and `adoptable` when the repo has a setup of its own to adopt. A gated lane it finds is `storyTools.lane`; the csf lane's scaffold is marked `csf: true` there, and is neither suggested nor adoptable. A Storybook with no gated lane beside it gives the suggested stories keys: `include` from the literal stories list of `.storybook/main`, and the command, port, `url` and `storyUrl` of the script that runs `storybook dev`; `storyTools.storybook` names the main config and notes what was not read. In a package of a workspace it also reads what the workspace root installs, and the story tool config kept there when the package holds stories; at a workspace root, its packages' dependencies name the framework and styling the root's own leave out. `monorepo` is also true for a root that holds packages and no framework of its own. A component glob it suggests always matches a file: one package per component is `packages/*/src/**`, and a repo with no component file gets none |
| `adopt.mjs` | `scan`: what the repo already has (story tools and lanes, a census of its `ds:` keys, its own graph, ratchet, token files, DESIGN.md and the script that writes them) and who depends on each; read-only, printed before init and written to `<project>/adopt/inventory.json` and `inventory.md` after; an entry of `tokens.styleFiles`, a path or a glob, that adds no style file is listed as a note, with the reason, in its summary and in the inventory. `plan`: the ledger and the proposed config. `config`: the proposal as a diff against the config, merged in with `--write` (it adds keys and never overwrites a value the user set; a config with comments is left for a hand edit). `status`: the ledger as a table. `mark <class> <state>`: moves a class (graph, stories, audit, tokens, docs) one state on through found, mapped, shadowed, proven, cut-over (with `--batch <id>`, the id its commit's `Adopt-Batch` trailer carries) and retired; never past a blocker, and never to retired when every asset of the class is kept; `--force` goes back or skips states, to repair the ledger. A new asset in a class past found takes its class back to found until it is agreed. `verify [<class>]`: massimo's graph, story lane, audit and token inventory set beside the repo's own (its generated graph or index, the lane as scan reads it now against `graph.json`, its ratchet by the ledger's map, its token inventory), as a table per class, exiting 1 on any difference the ledger has not accepted, or accepted with another detail; a class that cannot run (an empty or unreadable map, a newer file) is that class's difference and the others still run; `--against <file>` names the repo's file; `verify stories --pairs <file> --a <url> --b <url>` writes a `shoot.mjs` pairs file from the manifest, and `--shoot` runs it, with `--pairs` and `--out` read from `--root`. It records nothing. `accept <class> '<key>' --why <text>`: accepts a difference verify reports now, with the reason and its detail, and refuses a key verify does not report. It takes the flags verify takes (`--against`, and `--pairs`, `--a`, `--b`, `--shoot` and `--playwright`) for a difference only those flags produce. The detail it keeps leaves out what moves while the difference stays the same: a line number in the repo's page, and a shot's measured percentage. `config --lane csf` is the opt-in for a Ladle repo: the csf lane and Ladle's own settings, proposed from the saved inventory. `convert stories` (csf lane only) writes one record per story file and `removal.patch` under `<project>/adopt/stories/work/`, which ignores itself, the redirect map `<project>/adopt/stories/redirects.json`, and `<project>/adopt/stories/edits.md` once the ledger converts or retires the story tool; it lists the frozen candidates, `--freeze <file>` pins one, `--check` proves each file is unchanged outside its type import and each frozen file matches its hash, `--refreeze <file>` pins a frozen file again, `--types <file>` names the types file the patch points at, and `--ids-from <meta.json>` reads the old ids from Ladle's own list. On a csf lane, `verify stories --against <meta.json>` compares the lane's ids, files, exports and meta with that list and checks that every id the repo's specs, scripts and docs use resolves; `--sweep <base url>` opens every state on that server (`--legacy`, `--ready <selector>`, `--ids-from <meta.json>`, `--playwright <path>`, `--sweep-baseline <file>`, `--workers <n>`, `--timeout <s>`); with `--pairs`, `--a-route` and `--b-route` (templates with `{id}`, `{slug}`, `{state}`, `{scheme}`) and `--selector` apply, and `--workers <n>` reaches the shots with `--shoot`. `historical [<path>]`: marks a doc as a record of how things were, which retire leaves as it is, or lists them; it refuses a file code depends on. `retire <class> --dry-run`: what retiring a class takes out (its assets marked retire or convert, and the package scripts and workflow jobs that run them), any file that goes while a generator that stays still writes it (its code names the file), and every consumer still outside the historical docs, exiting 1 while one remains (on a csf lane, `--against <meta.json>` tells an id that was dead already from one the move loses, and a package script counts as the story tool's only when it runs the tool, directly or through npm, pnpm, yarn or bun running another script that does); without `--dry-run` it refuses, since deleting is the adopt skill's job |
| `stories.mjs` | `storybook [<file>...]`, on any lane beside a Storybook the repo keeps: each story's id by Storybook's own rule (the title, or the one Storybook builds from the file's path and the stories entry it matches, then the export's name) and its URL, read from `.storybook/main` and the story files without running either, for story files or for a component's stories in `graph.json` (its own story first); `--routes` prints the routes file `shoot.mjs --sweep` takes, and `--against <index.json or url>` compares the ids with Storybook's own index, a story of a file massimo did not list included when no file is named. ## Session protocol

Every skill follows this, so any session can be the next one.

**Begin.**

1. Run `node <project>/scripts/state.mjs show`. Read `<project>/STATUS.md`. Read `product.md` when the work touches design judgement.
2. Read the last ten lines of `decisions.md` when the phase builds on earlier choices.
3. If `STATUS.md` → Open questions holds something this phase needs, ask it before working.

**During.**

- Record each decision the user makes: `node <project>/scripts/state.mjs decide "<decision>" --why "<reason>" --phase <id>`. A decision is a choice someone could later ask "why?" about: a token value, a merge, a skipped component, a picked direction.
- Mark phase progress as it moves: `state.mjs set <phase> in_progress --note "<short progress, e.g. 18/40 primitives storied>"`.

**End** (including when the user stops mid-phase).

1. `state.mjs set <phase> <status> --note "<progress>"`. This also refreshes the progress block in STATUS.md.
2. Rewrite the hand-written sections of `STATUS.md`: Where we are (one short paragraph), Next step (one action and the skill that does it), Open questions, Last session (date, three bullets at most). Leave the generated block between the `massimo:progress` markers alone.
3. Offer to commit the project folder and the phase's code changes with a conventional message (`chore(design-system): …`, `feat(design-system): …`). Never push, open a PR, or merge unless the user asks.

## Writing for the reader

`STATUS.md`, `decisions.md` and handoffs are read by designers and developers who were not in the session. Write plain sentences, name files with repo-relative paths, and say what is not done. No session jargon.
